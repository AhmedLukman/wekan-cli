# Wekan API-to-CLI coverage

This tracker inventories every HTTP operation in the corrected Wekan v11.06 contract at [spec/wekan.corrected.yml](../spec/wekan.corrected.yml) and records whether this repository exposes an equivalent first-class CLI command.

User response decoding accepts notifications with absent, null, or populated read
timestamps, including `wekan auth status` and `wekan user current` (`GET /api/user`).
Workspace nodes map `id`, `name`, `icon`, and recursive `children`; unmapped
fields on a node or any child produce `protocol_error` in typed user responses.
Checklist and item detail reads map optional creator `userId` to `user_id`,
including records created by Wekan's UI through DDP. These commands use REST.
Detail operations #15 and #18 preserve denormalized `boardId` as `board_id`,
including the stale source board returned after a REST card move; requests use
the card's current board selector.

**Coverage:** 106 of 143 operations implemented (74.1%); 37 remaining.

Board card settings (#120–121) expose all 44 boolean controls and three aging
thresholds. Updates require at least one typed flag and preserve omitted fields.
Domain sharing (#136–138) uses native endpoints: listing requires site
administration, and valid writes preserve Wekan v11.06's HTTP 200
`not-authorized` defect as exit-5 `protocol_error` with native error metadata.
See [board settings and sharing](boards.md#card-settings-and-aging).

Integration operations #49–55 expose all seven native endpoints. Creation requires
a URL and uses server defaults. Update accepts explicit booleans, empty titles,
stdin token input or token clearing, and repeated activity values or array clearing.
Token flags conflict; activity replacement conflicts with clearing. Empty updates
send `{}`. Activity add/remove require at least one repeated `--activity` and send
JSON, including DELETE bodies. Inputs preserve order and duplicates. Only integration
deletion accepts `--yes`; activity removal runs directly. Update/delete acknowledgements
do not confirm a match, and update failures can follow earlier writes. See
[integration behavior](integrations.md).

Membership add/update support named roles and all eight boolean permission flags.
Update requires at least one permission input; named roles override individual
flags. Membership removals execute directly without `--yes`. Focused board lists
include inactive membership records; card lists project the selected array after
strictly decoding the complete detail response. These lists reuse existing GET
operations and add no operations to the total. Card mutation responses preserve
the requested card's stored arrays; linked-card requests mutate the source but
return the link's arrays, as described in [membership behavior](memberships.md).

Bulk card operations #29, #30, and #76 send one native request for 1-500
cards. Creation requires exactly one JSON array source; an optional top-level
swimlane is overridden by each card's nonempty `swimlaneId`. Bulk labels require
at least one `--add-label` or `--remove-label`; both options and `--card` may repeat.
Input order and duplicates are retained. Any item error or `notFound` entry
returns `batch_incomplete` (exit 5), with all outcomes in typed error details.
Bulk label results preserve existing null elements in `label_ids`.
Only bulk deletion accepts `--yes`; #29 preserves the pinned defect that retains
ordinary attachment metadata and file bytes after card deletion. Its `deleted`
array confirms card deletion only. Board label add #133 returns a new or reused
label ID; focused label lists reuse #63 and #128. See
[bulk card and label behavior](bulk-cards-and-labels.md).

The copy/move and card-read slice adds ten operations. Card counts use native
board/list count endpoints. ID-only card lookup can return archived cards;
scoped lookup retains its active-card filter. All six copy/move commands report
acknowledged IDs and `mutation_confirmed: false` in JSON, with unconfirmed effects
stated in human output; successful swimlane moves can also
insert an extra default lane asynchronously. Position flags conflict; card JSON
positions accept number/string/null, while list/swimlane JSON positions accept
all JSON types. All four copy operations preserve Wekan's HTTP-200 attachment
omission defect. See [copy and move behavior](copy-and-move.md).
Cross-board list moves apply the supplied swimlane as a source-card filter when
creating a destination list; an existing same-title destination bypasses that
filter and can transfer a card before HTTP 500.

## Status rules

- ✓ means a dedicated CLI command currently calls the operation.
- ✗ means no dedicated equivalent CLI command exists yet.
- Coverage counts HTTP operations, not support for every field or action available through an operation.
- Command cells include all command and global options. Typed commands accept `--output human` or `json`; attachment downloads additionally support raw output with `--destination -`.
- `--help` (also `-h`) displays command help without calling the API. The root-only `wekan --version` (also `wekan -V`) displays the CLI version.
- Multiple CLI commands may intentionally map to one API operation when Wekan selects behavior through the request body.
- Local-only commands such as `wekan profile ...` are excluded because they do not implement Wekan API operations.
- The generic `wekan api request` escape hatch does not count as dedicated operation coverage; a row becomes implemented only when a first-class typed command owns that operation.

Both list and card updates require at least one supported field flag. List WIP updates accept any subset of `--wip-limit`, `--wip-enabled`, and `--wip-soft`; omitted subfields take Wekan defaults. Card creation permits omitted, empty or explicit-null titles and descriptions. Card update supports same-board movement through `--swimlane-id` and `--list-id`; cross-board movement needs all three `--new-board-id`, `--new-swimlane-id`, and `--new-list-id` values. Set and clear forms of each card field conflict. `--labels` conflicts with both `--label` and `--clear-labels`; `--clear-starred` conflicts with `--starred`. Password stdin modes are mutually exclusive; raw password login conflicts with both code options.

Comment operations #21–23 preserve Wekan's accepted text, including U+0085.
Creation requires `--text` to be nonblank under JavaScript's whitespace rules;
the text is sent unchanged and Wekan trims JavaScript whitespace before storing it.

Checklist commands #13–20 require board/card selectors; item commands additionally
require a checklist selector. Checklist creation permits an omitted title and either
repeated `--item` titles or `--items` JSON (string, string array, or null); those
forms conflict. Item creation permits finite numeric `--sort` or `--sort-json`
(number, string, or null), which conflict. Item update allows no fields, title,
and either boolean `--is-finished` or `--is-finished-json` (boolean or string);
the completion forms conflict. Text and JSON wire types are preserved. Only
checklist and item deletion accept `--yes`.


Custom-field operations #31, #33–40, and #70 use explicit board scope. Definitions
accept seven pinned types; creation defaults settings to `{}` and supports four
boolean display flags, while update also supports `--always-on-card`. Updates
allow no fields. Settings accept explicit null for their four optional properties
and preserve null separately from omission in requests. Repeated dropdown `--item`
conflicts with exact JSON `--items`; card assignment text `--value` conflicts with
`--value-json`. Omission differs
from explicit null. Lookup uses a string path value and no list selector;
assignment requires the list selector. Lookup rejects empty values and the exact
values `.` and `..` before HTTP because the client's URL library cannot preserve
dot-only segments; Wekan itself accepts percent-encoded dots. Target IDs and other
selectors in these commands also reject dot-only segments before HTTP. Identifier
trimming follows Wekan's JavaScript rules, preserving U+0085 and trimming U+FEFF.
Supplied settings reject dropdown IDs that become `.` or `..` after Wekan's JavaScript
whitespace trimming. Only definition and item deletion accept `--yes`. Both
deletion prompts disclose their effect on all
boards associated with a shared definition; the board selector scopes the
lookup rather than limiting deletion to that board. See
[custom-field behavior and results](custom-fields.md).

## Operations

Dependency operations #25–28 and #41 are typed commands. The optional `--card`
selector switches listing from the board endpoint to the card endpoint. Create
and update preserve omitted, empty, and explicit null metadata; value/null forms
for the same field conflict. An empty update is sent to Wekan and fails with its
pinned HTTP 500 response. Only dependency deletion accepts `--yes`; update and
delete outputs report unconfirmed acknowledgments. See [dependency behavior](dependencies.md).

Attachment operations #108–119 are typed commands. Listing adds selectors in
board/swimlane/list/card order; `--list` requires `--swimlane-id`, and `--card`
requires `--list`. Adding each selector changes the endpoint as shown below.
Wekan v11.06 returns board-wide results at every list depth; output exposes both
requested and effective scope. Upload sources accept `-` for stdin with a required
filename. Downloads require an explicit path or stdout; raw/stdout and structured/file
forms conflict. Only deletion accepts `--yes`. See [attachment behavior](attachments.md).
